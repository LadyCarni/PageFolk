# What's New Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a What's new page that holds the roadmap ("Coming up"), the viewer's own feature requests and the changelog. Members can suggest and upvote features. The admin reviews requests, replies in per-item threads and manages the roadmap. Nav dots flag unseen versions (for everyone) and pending requests (for the admin).

**Architecture:** Roadmap items, votes and thread entries are new Prisma models. One `RoadmapItem` table covers member requests and admin items through a `status` field. The changelog is a typed array in code (`src/lib/changelog.ts`). Its lines reference roadmap items by their short `number`, and "shipped" is derived from that array, never stored. Server components load a view model from `src/lib/whats-new-view.ts`. Mutations go through server actions that wrap `src/lib/roadmap.ts`.

**Tech Stack:** Next.js 14 App Router, Chakra UI v2, Prisma on SQLite, Auth.js JWT sessions, Vitest against a real test DB (`npm test` resets it), Font Awesome.

**Spec:** `docs/superpowers/specs/2026-11-09-whats-new-design.md`. Read it alongside this plan. Its "The page", "Admin" and "The What's new dot" sections hold the exact copy and colors.

## Global Constraints

- Route: `/whats-new`. Admin page: `/admin/feature-requests`. The selected item lives in the query string as `?item=<id>`.
- Nav label is **What's new**, placed after Members and before Admin. Admin becomes a dropdown with **Books & club** (`/admin`) and **Feature requests**.
- Form copy, exactly:
  - title placeholder: "What feature would you like to see?"
  - description placeholder: "Describe what the feature does? What other apps have you used that has this feature, as an example?"
  - submit button: "Submit Feature Request"
  - cancel button: "Cancel"
  - note: "Every feature request is reviewed. Thank you for your idea!"
- Status colors:
  - In progress: text `dustyRose`, dot = new token `statusGreen` (`#7fbf8c`).
  - Planned: text `mist`, dot `antiqueGold`.
  - Status is plain uppercase small text with no box.
- Your-requests statuses: "Under review" (`mist`), "On the roadmap" (`antiqueGold`), "Shipped in X.Y" (`statusGreen`), "Not planned" (`borderMuted`).
- Crown icon: `faCrown` from `@fortawesome/free-solid-svg-icons`. The badge text is "Member request". Changelog lines show the crown alone at the start of the line, with `title`/`aria-label` "Member request".
- The What's new dot is `dustyRose`, about 8px, top right of the label, with a 2px `midnightPlum` ring. The Admin dot uses the same style.
- The thread composer is for the admin only. Everyone else sees "Only the admin replies here".
- Pending and declined items are visible only to their requester and the admin.
- Schema changes are additive only. Deploy runs `prisma db push`.
- No server-specific details in the repo (it's public).
- Follow existing patterns: `ValidationError` + `FormResult` for user-fixable errors, `requireUser`/`requireAdmin`, `revalidatePath`, and tests that clear tables in `beforeEach`.

## Review Focus

1. **A member opens `?item=<id>` for someone else's Under review or Not planned item.** Expect the same result as an unknown id: no panel, nothing leaked. Pinned in Task 3 and Task 5.
2. **A changelog line references a `number` with no matching row**, as in local dev or after a typo. The line renders as plain text with no crown and no link, and nothing throws. Pinned in Task 5.
3. **Approve or decline is clicked twice, or in two tabs**, for an item no longer under review. The second call is rejected with a ValidationError, and no second number is assigned. Pinned in Task 2.
4. **A blank, whitespace-only or overlong title/description/reply.** A validation message shows and nothing is saved. Pinned in Task 2 and Task 3.
5. **A double-tapped upvote races itself.** It ends in one vote, with no crash (P2002 handled like reactions). Pinned in Task 3.

- Schema:
  ```prisma
  model RoadmapItem {
    id                  String   @id @default(cuid())
    number              Int?     @unique   // assigned on approval or admin create
    title               String              // public wording
    description         String
    originalTitle       String              // as first written; shown at the top of the thread
    originalDescription String
    status              String              // 'review' | 'planned' | 'in_progress' | 'not_planned'
    isMemberRequest     Boolean
    authorId            String
    createdAt           DateTime @default(now())
    author  User          @relation("RoadmapAuthor", fields: [authorId], references: [id], onDelete: Cascade)
    votes   RoadmapVote[]
    entries RoadmapEntry[]
  }
  model RoadmapVote {
    itemId String
    userId String
    item RoadmapItem @relation(fields: [itemId], references: [id], onDelete: Cascade)
    user User        @relation(fields: [userId], references: [id], onDelete: Cascade)
    @@id([itemId, userId])
  }
  model RoadmapEntry {
    id        String   @id @default(cuid())
    itemId    String
    authorId  String
    kind      String   // 'reply' | 'event'
    body      String   // reply text, or event code: 'approved' | 'planned' | 'in_progress' | 'not_planned'
    createdAt DateTime @default(now())
    item   RoadmapItem @relation(fields: [itemId], references: [id], onDelete: Cascade)
    author User        @relation(fields: [authorId], references: [id], onDelete: Cascade)
  }
  ```
  Add the matching back-relations on `User`.
- `limits.ts`:
  - `FEATURE_TITLE_MAX = 100`
  - `FEATURE_DESCRIPTION_MAX = 2000`
  - `FEATURE_REPLY_MAX = 2000`

  - `submitRequest(authorId: string, title: string, description: string): Promise<RoadmapItem>`: status `review`, `isMemberRequest: true`, originals = the inputs.
  - `approveRequest(itemId: string, adminId: string, title: string, description: string): Promise<RoadmapItem>`: only from `review`. Sets the edited title and description, status `planned`, and the next number. Adds an `approved` event.
  - `declineRequest(itemId: string, adminId: string, note: string): Promise<void>`: only from `review`. Sets status `not_planned` and adds a `not_planned` event. A non-blank note is added as a `reply` entry after the event.

  - `setItemStatus(itemId: string, adminId: string, status: 'planned' | 'in_progress' | 'not_planned'): Promise<void>`: only from `planned`/`in_progress`. A no-op if unchanged. Otherwise adds an event with the new status code.

  - `pendingRequestCount(): Promise<number>`
  - Next number is `max(number) + 1` (starting at 1), inside the same `prisma.$transaction` as the update.

### Task 4: The What's new view model

**Files:**
- Create: `src/lib/whats-new-view.ts`
- Test: `tests/lib/whats-new-view.test.ts`

**Interfaces:**
- Consumes:
  - `CHANGELOG`, `shippedVersionByNumber`, `isNewerThan` (Task 1)
  - `canViewItem` (Task 3)
  - Prisma models (Task 2)
- Produces:
  ```ts
  type ItemStatusLabel = 'planned' | 'in_progress'
  type RoadmapCard = { id: string; number: number; title: string; description: string; status: ItemStatusLabel; isMemberRequest: boolean; votes: number; votedByViewer: boolean }
  type MyRequest = { id: string; title: string; display: { kind: 'review' } | { kind: 'roadmap' } | { kind: 'shipped'; version: string } | { kind: 'not_planned' } }
  type ChangelogLineView = { text: string; itemId: string | null; isMemberRequest: boolean }
  type ChangelogVersionView = { version: string; date: string; isNew: boolean; lines: ChangelogLineView[] }
  type ThreadEntryView =
    | { kind: 'original'; author: { id: string; name: string | null }; title: string; description: string; at: Date }
    | { kind: 'reply'; id: string; author: { id: string; name: string | null }; body: string; at: Date }
    | { kind: 'event'; text: string; at: Date }
  type ItemThread = { id: string; title: string; isMemberRequest: boolean; headerStatus: MyRequest['display'] | { kind: ItemStatusLabel }; entries: ThreadEntryView[] }
  type WhatsNewView = { roadmap: RoadmapCard[]; myRequests: MyRequest[]; changelog: ChangelogVersionView[]; selected: ItemThread | null }

  getWhatsNewView(viewer: { id: string; isAdmin: boolean }, lastSeenBefore: string | null, requestedItemId?: string): Promise<WhatsNewView>
  ```
- Rules:
  - **roadmap:** items with status `planned`/`in_progress` that aren't shipped, sorted with `in_progress` first, then by votes (descending), then `createdAt` (descending).
  - **myRequests:** the viewer's own `isMemberRequest` items, newest first. Shipped wins over any status.
  - **Changelog lines:** a line with a `roadmap` number that matches a row gets that row's `itemId` and `isMemberRequest`. An unmatched number gives `itemId: null, isMemberRequest: false` *(Review Focus 2)*. `isNew = isNewerThan(version, lastSeenBefore)`.
  - **selected:** null if the id is unknown or `canViewItem` is false *(Review Focus 1)*.
  - **Thread entries:** the original entry first, then entries by `createdAt`. A shipped item gets a final event "Shipped in X.Y" dated at that version's date.
  - **Event text** (using the event author's name, falling back to "The admin"):
    - `approved` → "{name} approved this"
    - `planned` → "Moved to Planned"
    - `in_progress` → "Moved to In progress"
    - `not_planned` → "Marked not planned"

  - the line for number 999 has `itemId: null` and `isMemberRequest: false`

  - `isNew` follows `lastSeenBefore` (`'1.0'` marks only `1.1` as new, and `null` marks all)
  - another member requesting a `review` item id gets `selected === null`, while its author and the admin get it
  - a declined request's thread entries are in order: original, "Marked not planned", reply
  - `myRequests` contains no other member's items
